# Design：spec-2026-11-severity-and-checks

## Context

動機見 proposal.md，要求見 specs/，逐條的規格與例子在 `features/*.feature`（2026.11.23 版）。現況：

- `scripts/smkul/entry.py` 的 `SEVERITY` 是「一種 `IssueKind` 對一個 `Severity`」，`Issue.severity` 照 `SEVERITY[self.kind]` 查。`Entry.is_clean()` 把 `ERROR`、`NOTICE` 當成不匯出；exit code 只看 `ERROR`。
- 「族語原句與詞素切割不符」只有一個 `IssueKind.SOURCE_SEGMENT_MISMATCH`，6 個小類放在 `detail` 的「分類:差異」裡，順序寫在 `parser.MISMATCH_WHY`；報告（`report.py`）與分析報告的 step 都要另外把它展開成小類。
- `parser.compare_source(source, segmentation)` 沒有族別；`_word_counts_fit` 只讓 `=` 併詞；`bare_form` 把 `:`、`_` 與 U+02BC 都去掉。
- `parser` 的詞素切割標點檢查（`_word_problem`）把 `+`、詞中間的 `.`、說話者標記記進 `entry.discuss`，給 `validate_glossing.discuss_chapter` 產生待討論章。
- `rules.check_correspondence` 只比切割符號的順序（`symbol_shape`），中綴在詞裡的位置不比。
- 字元正規化把 U+2018、U+2019 轉成 U+0027。
- 問題 ID（`proofreading.id_source`）由檔案、段編號、`issue.kind.value`、段的內文行算出來；老師已經在 `kithann/out/校對表/` 填過判斷，ID 一變，判斷就對不回去。
- behave 共 91 條：10 條斷言失敗、8 條 step 沒定義或對錯 step（`族別是 "{ethnic}"，詞素切割是 "{segmentation}"` 會把比對的 `族別是…，族語原句是…，對應詞素切割是…` 搶去對）。

## Goals / Non-Goals

**Goals：**

- 每一種問題只有一個嚴重度，嚴重度與排序只有一份正本，報告、匯出、校對表、exit code、step 都從那裡查。
- `features/` 全部轉青，`@規格要討論` 的照程式現在的輸出轉青。
- 已經填過的校對表判斷，ID 盡量不因為這次的拆分與引號正規化而變。

**Non-Goals：**

- 不做「詞根拆在中綴兩邊」的判斷（規格還在討論，照現在判通過）。
- 不改 `features/*.feature`（規格已定案）；改 step 時發現規格寫錯，回頭問使用者，不自己改 feature。
- 不改構詞判定（`構詞判定.feature` 的 `ai~au~i` 照現在的判定）。
- 不處理 `字元正規化.feature` 上尾三條分不出來的引號（照規則轉）。

## Decisions

### 決策 1：小類拆成獨立的 `IssueKind`，`SEVERITY` 改成照報告順序排的有序表

「族語原句與詞素切割不符」的 9 個小類、標點拆出來的兩種、中綴的兩種，都各自是一個 `IssueKind`，值就是 `features/分析報告.feature` 嚴重度表的「問題」欄（例如 `族語原句與詞素切割不符-只差一個字母`）。`SEVERITY` 改成跟那張表同順序的有序 dict，報告的問題表與第 7 章直接照它的順序排，不再特別展開不符的小類。

替代方案：保留一個 `SOURCE_SEGMENT_MISMATCH`，另外做「(種類, 小類) → 嚴重度」的表。缺點是報告、step、校對表都要繼續寫展開小類的特例，排序也要另外維護一份，所以不採用。

小類的說明文字（現在的 `MISMATCH_WHY`）改成照 `IssueKind` 查。`detail` 只放差異（`「l」→「r」`），不再放「分類:」前綴。

### 決策 2：問題 ID 用「大類」，拆分不改 ID

`IssueKind` 多一個「ID 用的大類」：不符的 9 個小類都用 `族語原句與詞素切割不符`，標點拆出來的兩種用 `詞素切割有標點`，其他種類的大類就是自己。中綴的兩種是新判法，以前同一段可能判成「符號不一樣」、「沒有切」或通過，對不到一個固定的舊名稱，所以用自己的名稱，ID 會變。`id_source` 改用大類，所以「只差一個字母」改判成「族語和華語不一致」，或 `Yu:` 從「詞素切割有標點」拆出去，ID 都不變，老師的判斷照樣對得回去。

### 決策 3：引號統一成 U+02BC，但算 ID 時折回 U+0027

正規化後內文行的 `'`、`’` 都變成 `ʼ`，有 5462 行會變。`id_source` 算 sha256 前，把內文行的 U+02BC 換回 U+0027，跟這次改版以前的內容一樣，ID 不變。

所有比對喉塞音的地方 SHALL 一起認 U+02BC：`bare_form`、`SEGMENT_SYMBOLS`、`markers.UNCERTAIN`（排灣語 `'I`、`'A`）、ODS 清單讀進來的形（清單本身也要正規化，不然 `'` 跟 `ʼ` 對不上）。

「當引用符號用的引號不轉」寫成一支看前後字元的函式，四條規則照 spec 的順序判斷。

### 決策 4：比對帶族別，`compare_source(source, segmentation, ethnic="")`

族別用 `languages.split_kind` 的短名（`阿美`、`泰雅`、`太魯閣`、`賽德克`）。族別影響三件事：

- `_word_counts_fit`：`=`、`.` 都可以併詞；泰雅另外加 `+`。
- 阿美語保留 `:`：`bare_form` 多一個參數，阿美語把 `:` 當字母留著；判成不符時，若去掉 `:` 就相同，歸「只差長音符號」。
- 泰雅語群（泰雅、太魯閣、賽德克）：小類是「只差一個字母」「差 2-3 個字母」「長度差很多」的，`passed` 設成通過，不記問題。

小類的先後照 spec：拉長音（詞素切割有 `==`，先檢查，`bare_form` 會把 `=` 去掉）→ 族語和華語不一致（逐詞對位，一邊 `bare_form` 全是拉丁字母、另一邊全是漢字）→ 只差長音符號 → 原本的 6 類。族語華語的逐詞對位只在兩行詞數一樣時做，詞數不一樣就跳過這一類。

族別沒給（空字串）時，所有限定語言的規則都不套用，單元測試照舊能跑。

### 決策 5：中綴的分類在符號比對之前做

`check_correspondence` 逐個 token 先看中綴：

1. 詞素切割的 `<…>` 後面沒有字母（詞尾，或直接接切割符號）→ 通過（中綴後面沒有詞根）。
2. 詞素翻譯的 `<…>` 前面有字母、後面沒有字母（詞尾，或直接接切割符號）→ 兩邊符號順序一樣算「詞根放在中綴前面」，不一樣算「詞綴黏在中綴前面，切割符號在中綴後面」。
3. 詞素翻譯的 `<…>` 前後都有字母、中間沒有切割符號 → 通過（詞綴黏在中綴前面、或詞根拆兩邊，都先不判）。這一條也蓋過照符號比會判成「詞素切割有切，詞素翻譯沒有切」的情形。
4. 其他照原本的符號比對。

拿 feature 裡的 12 組例子驗證過分界（`r<m>ngaw`、`pa<i>tas-an`、`'u=pa-s<em>alav-an`、`ka<i>kuza'-an`、`p<in>ataz`、`na-k<em>eljang`、`ma<i>-langna`、`levul<en>`……）。

### 決策 6：共用 step 放 `features/steps/共用.py`，各 When 把結果的問題清單放進 `context.issues`

「嚴重度是 "…"」在比對、標點、對應三個 feature 都有，behave 的 step 是全域的，只能定義一次。三個 feature 的 When 都把這次檢查得到的 `Issue` 清單放進 `context.issues`，共用 step 取最後一筆的嚴重度比。比對的新 When 句型是 `族別是 "{ethnic}"，族語原句是 "{source}"，對應詞素切割是 "{segmentation}"`；標點原本的 `族別是 "{ethnic}"，詞素切割是 "{segmentation}"` 改用 regex matcher，限定族別裡面不能有 `"`，不再搶比對的句子。

### 決策 7：說話者切段在重組之前做，段號是字串

`parser` 在判斷排法時先認說話者標記（1 到 3 個字母加 `:`／`：`）。對話段（每行都有標記、兩套四行）與兩位發音人一組（詞素切割、詞素翻譯照標記分組）切成多個 `Entry`，`number` 是 `13-1`、`13-2`，時間碼共用。族語原句、華語翻譯切不成同樣份數的，整段不切、記「行黏在一起」（就是現在的行為）。段號排序（校對表、報告）要能排 `13-1` 在 `13` 與 `14` 中間。

## Risks / Trade-offs

- [IssueKind 拆分會讓 `程式裡沒有這張表以外的問題種類` 那條 step 比較敏感] → `SEVERITY` 的順序就是表的順序，step 逐列比對，多一列少一列都會紅，正好當保護。
- [引號正規化讓翻譯訓練YAML 的內容大量改變（`'` → `ʼ`）] → 這是規格要的；在報告的「自動處理」章列出筆數，下游要知道換了字元。
- [ODS 清單、`markers.UNCERTAIN` 漏改，`'I` 變 `ʼI` 後就判不出是不確定標記] → 構詞判定的 feature 有 `'I` 的例子，跑 behave 會抓到；另外補單元測試。
- [泰雅語群放寬後，真正打錯字的段也會通過] → 規格的決定；這三種語言的詞素切割寫完整形是常態，老師另外校對。
- [族語和華語不一致只在詞數一樣時判得到] → 詞數不一樣時會落到「多處不同」或「長度差很多」，報告的說明寫清楚。
- [說話者切段的段號改變校對表的「段」欄與 ID] → 這些段原本整段判成「行黏在一起」，切開後本來就是不同的問題，ID 變是對的。

## Migration Plan

1. 先改嚴重度架構（決策 1、2）與共用 step，不改判法，確認現有的青的還是青的。
2. 再逐個 feature 改判法：字元正規化 → 族語原句比對 → 標點 → 對應 → 排版分析 → 分析報告。每做完一個跑一次 behave 與單元測試。
3. 最後用使用者指定的語料目錄跑一次 `validate_glossing`（跑之前要先問用哪一版），看報告與校對表的筆數變化，跟使用者確認。

回退：每一步都是獨立的提交範圍，有問題就整步撤回。

## Open Questions

- 老師已經填過的校對表，是不是有用到被拆出去的問題（例如 `Yu:` 那 20 處以前記成「詞素切割有標點」）？決策 2 讓 ID 不變，但校對表的「問題」欄名稱會變，要不要在校對表標示「問題名稱有改」？
- 報告的「自動處理」章，引號那一項的筆數要不要分「轉了」與「當引用符號沒轉」兩個數字？
