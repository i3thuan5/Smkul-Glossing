# Design: proofreading-sheet

## Context

動機見 proposal.md，要求見 specs/。現況：

- `scripts/validate_glossing.py` 的 `collect()` 走過全部 docx，把每段的 `Issue` 收起來，再交給 `report.py` 產生 glossing_report.md。`Entry.is_clean()` 決定匯不匯出 YAML。
- `Issue` 有 `kind`、`path`、`number`、`detail`、`compare`，沒有 ID。
- 專案原則是能用 stdlib 就不加依賴（採購安全說明書；之前 python-docx、odfpy 都因此不用）。`markers.py` 已經用 `zipfile` ＋ `ElementTree` 讀 ODS，`docx2text.py` 讀 docx。
- `kithann/` 整個不進版控，語料、報告、校對表都只在工作目錄。
- 這個 change 在 `segment-punctuation` 之後做，嚴重度有四級：錯誤、錯誤（照常匯出）、警告（照常匯出）、現象。

## Goals / Non-Goals

**Goals：**

- 老師只要會用 Excel 或 Google 試算表的下拉選單就能校對，不用懂程式、不用懂 ID 怎麼算。
- 老師填過的判斷，重跑幾次都還在；docx 改過的段會自動重新檢查。
- 不加任何第三方套件。

**Non-Goals：**

- 不做線上同步（不串 Google API）。檔案靠人上傳、下載。
- 不處理 docx／txt 一致性報告的問題。那份報告是在比 txt，而 YAML 已經決議只從 docx 產生。
- 不讓老師在校對表裡直接改語料；要改的話還是改 docx。

## Decisions

### 決策 1：用 xlsx，不用 CSV 或 ODS

| 格式 | 下拉選單 | Excel | Google 試算表 | stdlib 寫得出來 |
|---|---|---|---|---|
| CSV | 沒有 | 能開，但 UTF-8 中文常變亂碼 | 能匯入，要另外手動設下拉選單 | 能 |
| ODS | 有 | 能開 | 匯入後下拉選單不一定保留 | 能 |
| **xlsx** | **有**（`dataValidation`） | **原生** | **上傳後直接轉換，下拉選單保留** | **能**（zip ＋ XML） |

會議決議寫的是「google sheet 或 excel」，xlsx 兩邊都能直接用，老師拿到檔案打開就能填。探索時原本的流程是「CSV → Google → 下載 ODS」，改用 xlsx 後少掉手動設下拉選單這一步，交回時也是同一種格式。

新增 `scripts/smkul/xlsx.py`，只做這次需要的部分：寫（多個分頁、第一列是標題並凍結、字串儲存格用 inline string 不用 sharedStrings、一欄的下拉選單、儲存格內部分文字紅色粗體），以及讀（讀所有分頁的字串值；Excel 存檔會改用 sharedStrings，所以讀的時候兩種都要支援）。

**替代方案**：用 openpyxl。功能完整，可是要通過採購安全審查，而且我們只需要很小的一部分功能，不值得加依賴。

### 決策 2：ID ＝ `ISSUE-` ＋ sha256 的前 8 碼

輸入是 `檔案路徑`、`段編號`、`問題種類的值`、`段內容` 用 `\n` 接起來；段內容是 `Entry.body`（那一段的全部內文行），所以 docx 改了一個字 ID 就會變。沒有段的問題（檔案層的問題、孤兒時間碼）用 `detail` ＋ `compare` 代替段內容。

8 碼十六進位有 43 億種組合，全語料幾千筆問題，撞號機率可以忽略；萬一撞號，產生校對表時檢查一下，有重複就報錯（程式錯誤，不是語料錯誤）。前面加 `ISSUE-`，一看就知道是問題編號，也避免 Excel 把 `12e45678` 這種 ID 當成數字。用 sha256 是 stdlib `hashlib` 就有的標準雜湊。

**替代方案**：用流水號。重跑或語料一改，號碼就全部錯開，舊的判斷對不回去。

### 決策 3：ID 在 `collect()` 算，判斷在匯出前套用

流程：

```
parse_corpus_file ──▶ entry.issues ──▶ 算 ID ──▶ 讀 kithann/校對/ 的判斷
                                                    │
                       ┌────────────────────────────┤
                       ▼                            ▼
            「程式判斷錯」移出 entry.issues     其他照舊
            放進 confirmed 清單                     │
                       │                            ▼
                       └──────▶ is_clean() ──▶ YAML、報告、校對表
```

`Issue` 新增 `id` 欄位。新增 `scripts/smkul/proofreading.py`，負責：算 ID、讀回判斷（多檔合併、取較新、記錄讀取問題）、把確認是程式判斷錯的問題從 `entry.issues` 移到另一個清單、產生新的校對表（帶入舊判斷、整理「已不存在的紀錄」）。`validate_glossing.py` 只負責串起來。

被移出的問題不再影響 `is_clean()`，所以只剩這種問題的段會匯出——符合 spec「程式判斷錯的問題不再算問題」。

### 決策 4：校對表的列放四行語料，問題位置標紅

老師要判斷「程式對不對」，需要看到四行語料，不能只看提示。欄寬給固定值，提示欄跟語料欄自動換行。

標紅用 xlsx 的 rich text（儲存格裡分成幾段 `<r>`，有問題的那段加紅色粗體 `<rPr>`），儲存格的純文字不變，程式讀回時也不受影響。位置怎麼算：

- 「詞素切割有標點」：重跑 segment-punctuation 的標點檢查函式，拿到有問題的詞的位置（第幾個詞），換算成字元範圍。
- 「族語原句與詞素切割不符」：`bare_form()` 改成可以同時回傳「每個字母在原字串的位置」，`difflib` 比出不一樣的範圍後，換回原字串的位置標紅。
- 其他種類不標。

位置在產生校對表時才算，不存在 `Issue` 裡，`Issue` 只多一個 `id`。

### 決策 5：「已不存在的紀錄」放在同一個語言別的檔案裡

讀回來的判斷，依 ID 分到它原本所在的語言別（從讀回來那一列的「檔案」欄推出族別、語言別）。對不到這次任何問題的，寫進那個語言別 xlsx 的第二個分頁。只保留有判斷或有備註的列，空白的列不留。

### 決策 6：老師交回的檔案放 `kithann/校對/`，跟輸出分開

程式寫 `kithann/out/校對表/`，讀 `kithann/校對/`。分開是因為 `kithann/out/` 每次重跑都會被蓋掉；老師的檔案要是放在那裡，下次重跑就不見了。報告的「校對流程」一節寫明「從 out 拿去給老師，填好的放回 校對」。

## Risks / Trade-offs

- [Google 試算表轉換 xlsx 時，下拉選單可能跑掉] → 實作時要真的上傳一次 Google 雲端硬碟驗證（tasks 有這一項）；如果跑掉，報告的校對流程寫「請用 Excel 開，或在 Google 試算表裡選『資料 → 資料驗證』確認」。
- [Google 試算表轉換 xlsx 時，儲存格內的部分紅字（rich text）可能變成整格同色或消失] → 標色只是輔助，文字不變；由使用者實機確認，跑掉的話報告註明「標色請用 Excel 看」。
- [老師一改 docx，那一段所有問題的判斷都失效，包括跟改的地方無關的問題] → 這是刻意的：段改了就重新檢查一次比較安全，失效的判斷也會留在「已不存在的紀錄」分頁，老師可以照抄。
- [好幾位老師各自交回同一個語言別的檔案，判斷互相矛盾] → 以檔案修改時間較新的為準，並在報告列出矛盾，開會時處理。
- [問題數量多（全語料幾千筆），校對表很長] → 一個語言別一個檔，而且照檔案、段排序；老師可以用試算表的篩選功能只看自己負責的檔案或問題種類。

## Migration Plan

第一次執行時 `kithann/校對/` 不存在，等於沒有任何判斷，報告只多了 ID 與三個空的章節，YAML 不變。之後隨老師交回的校對表逐步生效。要退回的話，把 `kithann/校對/` 移走再重跑，結果就跟沒有這個功能一樣。
