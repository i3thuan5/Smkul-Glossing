## Context

現在 `parse_timecode` 用 `NUM_TIME` 認時間碼行，回傳原字串的開始、結束與格式名（看分隔符：`-->`、`,`、`–`、`-`），`Entry.start`、`Entry.end` 存原字串，翻譯訓練YAML 直接寫出去。比先後用 `timecode_parts` 把數字拆成 tuple 照欄位比。檔案用了兩種以上格式記「時間碼格式混用」，用了連字號式記「時間碼單位不明」。

全語料（語料標註語料_20261118）掃描的結果：認得出的時間碼行 12817 行；毫秒一兩位數 149 行（中排灣 1、2、4、5，泰雅 1）；`-->` 配小數點 20 行（南排灣 3）；看起來是時間碼卻認不出的 17 行，其中 12 行前一行是編號行。中排灣 4 個檔的毫秒照小數讀有 26 處前後段重疊，照整數毫秒讀是 0 處。

規格以 `features/時間碼.feature`、`features/分析報告.feature`（2026.11.24）為準。

## Goals / Non-Goals

**Goals:**

- 翻譯訓練YAML 的開始、結束只有兩種值：SRT 字串，或數字 `-1.0`。
- 時間的解讀只在 parser 一個地方做，每一種寫法對到一條 feature scenario。
- 打錯的時間碼行不再把兩段併成一段。

**Non-Goals:**

- YAML 不另外保留原字串（原字串在 docx 與報告的問題說明裡）。
- 不處理 `@規格要討論` 的三種：編號黏在時間碼前面、時間碼拆成兩行、時間碼後面黏著族語原句。
- 不檢查「這一段的開始比前一段還早」（霧台 2 有 2 段），只檢查同一行的結束早於開始。
- 不對錄音驗證 30fps 與省略 0 的推斷。

## Decisions

### 1. 換算放在 parser，`Entry` 存換算後的值

`parse_timecode` 照樣回傳原字串（給報告的問題說明、格式表的例子用），另外加一個換算函式，輸入原字串與格式名，輸出 SRT 字串或「不能用」的原因。`split_entries` 用換算結果建 `Entry`：`start`、`end` 是 SRT 字串或 `NO_TIME = -1.0`。

替代方案：`Entry` 同時存原字串與換算值，到匯出 YAML 才換算。缺點是兩份值容易用錯欄位，而且報告、YAML 會各自判斷能不能用；換算一次、問題在 parser 記好比較單純。

### 2. 格式名照分隔符加小數點判斷

`-->` 且毫秒用 `.` 的叫「`-->` 配小數點」，其他照舊看分隔符。格式名只用在報告的時間碼表（檔數），換算規則只分兩類：有毫秒的四種（`時:分:秒` 加小數）與連字號式（`分:秒:影格`）。

### 3. 檢查順序：毫秒位數 → 換算 → 先後

1. 有毫秒的寫法，開始或結束的毫秒不是三位數 → 「時間碼毫秒位數不對」，`-1.0`，不再做先後檢查（毫秒讀不準，比先後也不準）。
2. 換算成總毫秒數：`時:分:秒.毫秒` 直接算；連字號式 `分*60000 + 秒*1000 + (影格*1000 + 15) // 30`，用整數算四捨五入，不用 Python 的 `round`（偶數捨入，0.5 會捨掉）。
3. 結束 < 開始 → 「結束時間早於開始」，`-1.0`。

`timecode_parts` 換成比總毫秒數。原本照欄位比、毫秒當整數，剛好跟「省略 0」的讀法一樣，所以這次改法不會讓既有的「結束早於開始」判斷結果變。

### 4. 時間碼行打錯在找段界時判斷

`_entry_starts` 找段起頭時，除了 `parse_timecode` 認得的行，再加一種：前一個不是空白的行符合 `NUM_ONLY`，這一行有 `\d\s*[:;]\s*\d`、卻 `parse_timecode` 不出來。這一行當成時間碼行，解析結果標成「打錯」，編號取前一行。`split_entries` 看到打錯的標記，`start`、`end` 記 `-1.0`，記一筆「時間碼行打錯」，說明附原字串。

只認「前一行是編號行」的，是為了不誤判：族語原句、華語翻譯裡很少出現`數字:數字`，而且前一行又剛好是只有數字的行。全語料這個條件只命中 12 行，全部是真的時間碼行。

### 5. 問題記在第一段

照說話者切開的段共用一組時間碼，三種時間碼問題跟「結束時間早於開始」現在的作法一樣，只記在第一段；每一段的 `start`、`end` 都設成一樣的值。

### 6. 刪掉「時間碼格式混用」

`IssueKind.MIXED_TIMECODE_FORMAT` 與它的 `SEVERITY`、`KIND_WHY` 一起刪；`split_entries` 不再記。報告「筆數的算法」那句說明拿掉「時間碼格式混用」。`timecode_formats` 照樣收集，給時間碼表用。

### 7. step

`features/steps/時間碼.py`：

- `開始是`、`結束是` 改比換算後的值。
- 新 step：`開始與結束都是 -1.0`、`記一筆「…」`、`這個檔案記一筆「…」`：把「編號行＋時間碼行」餵給 `parse_text`，從段或檔案的問題找，並設 `context.issues` 給共用的 `嚴重度是`。
- 段層級：`第 N 段的開始與結束都是 -1.0`、`第 N 段記一筆「…」`，接在 `讀入這幾行` 後面用。

## Risks / Trade-offs

- [30fps 推斷錯了，霧台的時間整個不對] → 「時間碼單位不明」照樣記，報告說明是推斷、請對方確認；換算只在一個函式，改 fps 只改一個常數。
- [下游讀 YAML 的程式還在當原字串解析] → proposal 標 BREAKING；`-1.0` 是數字、正常值是字串，型別就分得出來。
- [「時間碼行打錯」誤判，把一行標注當成時間碼] → 條件要「前一行是編號行」加`數字:數字`；apply 時跑全語料，確認只命中預期的 12 行。
- [毫秒位數不對的 149 段時間不能用] → 是故意的：讀法只是推斷，請老師照錄音補齊；段照常匯出，不影響翻譯訓練。
