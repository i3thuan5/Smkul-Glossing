# Design: meeting-terms-yaml

## Context

動機見 proposal.md。現況：

- staged 的程式已經把 YAML 改成「檔案 → 段」，key 用 `族語原句`、`詞素切分`、`詞素翻譯`、`華語翻譯`、`語言別`、`語言別代號`、`段`，並新增 `scripts/smkul/languages.py` 查語言別代號。其中 `詞素切分` 跟會議決議的「詞素切割」不一樣，要改。
- 舊用語分布很廣（含 feature 例子的標籤）：「切分」約 490 處、「gloss」約 550 處、「組」約 600 處、「族語」約 170 處、「翻譯」約 180 處。
- 這些詞**不是每一處都指語料的某一行或某個單位**，所以不能整批取代（見決策 2）。
- 「段」原本就有兩種意思：長句被拆成的那幾截（`長句分段重組——兩段`、`缺 gloss 段`），以及 docx 的段落（`docx2text.py`）。現在「段」要接手原本「組」的意思。

## Goals / Non-Goals

**Goals：**

- 全專案只有一套用語，`組`、`切分`、`gloss`、`原文` 這幾個舊稱在指語料的行或單位時不再出現。
- 「段」只剩一種意思：一個編號加時間碼的語料單位。
- 構詞資訊完全不進報告和 YAML，但 `features/構詞判定.feature` 和它的 step 照樣跑得過。

**Non-Goals：**

- 英文識別字（`Entry`、`entries`、`segmentation`、`gloss` 等）不全面改名，只改意思已經變了的（見決策 5）。
- 不修改 `features/構詞判定.feature` 的判定規則，只換用語。
- 不處理會議的其他決議（見 proposal.md）。

## Decisions

### 決策 1：用語對照表

| 舊稱 | 新稱 | 說明 |
|---|---|---|
| 族語、原文、族語原文（指第一行） | 族語原句 | |
| 切分、構詞切分（指第二行） | 詞素切割 | 會議原文是「詞素切割」，staged 程式的 `詞素切分` 要改 |
| 切分行 | 詞素切割行 | |
| gloss、glossing（指第三行） | 詞素翻譯 | |
| gloss 行 | 詞素翻譯行 | |
| 翻譯（指第四行） | 華語翻譯 | |
| 組 | 段 | 「第 26 組」→「第 26 段」、「組數」→「段數」、「組編號」→「段編號」 |
| 語別 | 語言別 | 「依語別統計」→「依語言別統計」 |
| 切分符號（`-`、`=`、`<>`、`~`） | 切割符號 | |
| 長句分段 | 長句換行 | |
| 長句拆成的「段」 | 截 | 「兩段」→「兩截」、「切分段」→「詞素切割截」 |
| 缺 gloss 段 | 缺詞素翻譯行 | |
| 缺翻譯行 | 缺華語翻譯行 | |
| 詞裡切出來的「段」 | 詞素 | 「哪一段是詞根」→「哪一個詞素是詞根」 |
| 詞素翻譯用 `.` 串的「第一段」 | 第一個屬性 | |
| 「少了一整段」 | 少了一整串 | |

衍生的分類名照表組合，例如：

| 舊分類名 | 新分類名 |
|---|---|
| 原文與切分不符-詞數不同（等 6 類） | 族語原句與詞素切割不符-詞數不同 |
| gloss 的詞比切分少 | 詞素翻譯的詞比詞素切割少 |
| gloss 的詞比切分多 | 詞素翻譯的詞比詞素切割多 |
| 切分沒有切，gloss 有切 | 詞素切割沒有切，詞素翻譯有切 |
| 切分有切，gloss 沒有切 | 詞素切割有切，詞素翻譯沒有切 |
| 長句分段重組——兩段 | 長句換行重組——兩截 |

feature 檔名：`原文切分比對.feature` → `族語原句詞素切割比對.feature`、`切分與glossing對應.feature` → `詞素切割與詞素翻譯對應.feature`。

「空組」照「組 → 段」改成「空段」。

**沒有改的詞**：`詞素`、`token`、`純華語句`（這裡的「句」是說話的句子，不是語料單位）、`行黏在一起`、`重複標註`、`孤兒時間碼`。

### 決策 2：不能動的地方

改名一律人工逐處判斷，用 grep 列出候選，不用 sed 整批取代。下列地方不改：

| 不改 | 例子 | 原因 |
|---|---|---|
| 反引號內的語料、ODS 原文 | `族語範例`（ODS 欄名）、`使用族語的情況已經少見了` | 原始資料 |
| 語料路徑 | `說族語在大漢部落的過.docx` | 檔名 |
| 外部文件名 | 《常用構詞標記清單》、`原語會提供-常用構詞標記清單_0713.ods`、`族語及語言別名稱 - 語言別名稱.csv` | 別人的文件 |
| 「族語」當「原住民族語言」用 | 族語 AI、族語語料 | 不是指第一行 |
| docx 的段落 | `docx2text.py` 的「段落」 | 跟語料單位的「段」用不同的詞分開 |
| 「組」當「一組例子」用 | CLAUDE.md 的「3 組例」 | 不是語料單位 |
| 封存的 change、會議議程 | `openspec/changes/archive/`、`kithann/2026.09 …議程.md` | 歷史紀錄 |

### 決策 3：「段」的歧義

「段」改成語料單位之後，長句那幾截改叫「截」，docx 段落一律寫「段落」，構詞判定與對應檢查裡「一個詞切出來的一塊」改叫「詞素」（實作時才發現這第三種用法，使用者選了「詞素」）。考慮過的替代：

- 長句改叫「行」（兩行、三行）：每一截本身就有兩行（詞素切割、詞素翻譯），「兩行」會被誤會成總共兩行。不採用。
- 長句改叫「換行一次／兩次」：可行，但跟「三截」「四截」的統計說法接不起來。不採用。

### 決策 4：構詞判定怎麼暫停

- `validate()` 只做詞素切割行與詞素翻譯行的對應檢查，不再做構詞判定，也不再回傳不確定標記和判不出來的詞素。`collect()` 的 `uncertain`、`undecided` 跟著拿掉。
- 報告拿掉：總覽的「構詞無法判斷」、`hard_morphology_section`、`uncertain_section`、`todo_section` 裡的「構詞判斷困難的詞素要怎麼處理」。
- `analyse_word`、`classify`、`Word`、`Morpheme`、`MarkerList` 留著，`features/steps/構詞判定.py` 還在用。`Word.to_yaml()`、`Morpheme.to_yaml()` 已經沒人用，刪掉。
- ODS 仍然要讀：「語料格式說明」章的「語料目錄與 sheet 對應表」要用。
- `構詞判定.feature` 檔頭加一段說明「草稿，暫停維護，報告與 YAML 不使用」。

考慮過把構詞判定的程式整個刪掉，但使用者決議留作內部草稿，所以只是不接進流程。

### 決策 5：英文識別字只改意思變了的

CLAUDE.md 要求變數名用華語，但專案現有的識別字大多是英文，全面改名不在這次範圍。這次只改英文意思已經對不上的：

- `IssueKind.MISSING_GLOSS_SEGMENT` → `MISSING_GLOSS_LINE`
- `yamlout.write()` 的 `sentences` → `segments`（staged 已改）；`validate_glossing.py` 的 `yaml_sentences`、`exported_sentences` → `yaml_segments`、`exported_segments`

測試方法名是華語的（例如 `test_句_yaml_的_key`），照對照表改。

### 決策 6：語言別代號的查法

YAML 的 `族別`、`語言別` 從目錄名取得，跟 CSV 的「語言別」欄（族語標準全名）寫法不同，所以依序試：`語言別＋族別＋語`（秀姑巒阿美語）、`語言別＋語`（中排灣語）；族別和語言別一樣時試 `族別＋語`（太魯閣語）。每個候選另外試把「台」換成「臺」（霧台 → 霧臺）。查不到寫空字串，不擋匯出。現有 11 個語料目錄都查得到。

考慮過在程式裡寫死一張目錄 → 代號的對照表：比較直接，但 CSV 是對方的正式來源，新增語言別時只要更新 CSV。不採用。

CSV 原本在 `kithann/規範/`，但 `kithann/` 整個不進版控，CI 上沒有這份檔案，`CorpusFile.to_yaml()` 會失敗（實作時才發現）。使用者決定把 CSV 複製一份到版控內的 `scripts/smkul/data/族語及語言別名稱 - 語言別名稱.csv`，程式與測試都讀這份，路徑以 `languages.py` 所在的目錄為準，不依賴執行時的工作目錄。這份是公開的 42 個語言別代號表。考慮過的替代：測試另用 `tests/data/` 的小 CSV（跟 ODS 一樣），或找不到 CSV 就 skip 測試。`kithann/規範/` 的版本以後更新時，要手動同步這份副本。

### 決策 7：scenario 名稱含舊用語的 requirement 整條換新名稱

openspec 的 MODIFIED 不准丟掉或改名舊的 scenario，同一個 requirement 名稱也不能同時出現在 REMOVED 和 ADDED。所以 scenario 名稱含舊用語的 8 條，一律 REMOVED 舊的、ADDED 新名稱的，新的 requirement 開頭註明「這條取代原本的 ×××」：

| 舊名稱 | 新名稱 |
|---|---|
| 單一 YAML 匯出 | YAML 匯出結構 |
| markdown 報告 | 報告內容 |
| 組結構辨識 | 段結構辨識 |
| 長句分段重組 | 長句換行重組 |
| 字元正規化 | 字元正規化與計數 |
| 結構異常偵測與分類 | 段結構異常偵測與分類 |
| 原文嚴格檢查切分 | 族語原句嚴格檢查詞素切割 |
| 切分行與 gloss 行對不起來的分類 | 詞素切割行與詞素翻譯行對不起來的分類 |

只有 requirement 名稱含舊用語、scenario 名稱沒有的，用 RENAMED＋MODIFIED（檔頭註記與段內元註記、逐段結構比對）。

考慮過保留舊 scenario 名稱、封存後再手改主 spec：requirement 名稱可以不動，但要繞過正式流程。使用者選了整條換掉。

「報告內容」和「段結構異常偵測與分類」是整條照搬原本的內容，說明超過 500 字，`openspec validate` 會出 warning。一般驗證會過，`--strict` 會擋。

## Risks / Trade-offs

- [漏改舊用語] → tasks 最後一步用 grep 掃 `組`、`切分`、`gloss`、`原文`、`語別`、`分段`，逐筆確認剩下的都在決策 2 的例外裡。
- [誤改反引號內的語料] → 改完看 diff，只要反引號內有變動就退回。
- [報告的「詳見 `features/xxx.feature`」指到舊檔名] → 改檔名和改引用放在同一個 task。
- [會議議程的 GitHub 連結指到舊檔名] → 那些連結釘在 commit 上（`blob/7644c52…`、`blob/18294bc…`），不會斷，不處理。
- [YAML 的 key 改了，對方已經拿到的舊 corpus.yaml 對不上] → 對方是在會議上才看到 YAML，這次一起重新產生。
- [CLAUDE.md 是使用者的規定] → 動 CLAUDE.md 的 task 要使用者先同意。

## Migration Plan

1. 先改 spec 和 feature（規格），behave 會變紅，這是預期的。
2. 改 steps，讓 behave 回到全綠。
3. 改程式，一支一支來：先改測試、確認紅的原因對，再改程式、確認同一個測試轉綠，才換下一支。`validate_glossing.py`、`check_docx_txt.py` 原本沒有測試，先補 `tests/test_validate_glossing.py`、`tests/test_check_docx_txt.py`。最後 `tox` 全綠。
4. 重新產生 `kithann/out/` 的 YAML 和報告，人工抽看。
5. grep 掃一遍舊用語。

不需要回滾計畫：`kithann/out/` 不進版控，重跑就會產生。
